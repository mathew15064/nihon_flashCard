## Bug fix — swipe did not advance to next card

### Bug
Swipe gesture was detected visually (card followed pointer, badge showed),
but after committing, the next card never became visible — session appeared stuck.

### Root cause
`flyOut()` set `opacity: 0` on the card for the fly-out animation, but
`resetCardPosition()` only cleared `transform`/`transition` — never `opacity`.
The answer pipeline actually completed (API succeeded, `nextCard()` ran,
`renderCard()` rendered) but every subsequent card stayed fully transparent.
Two related defects in the same handler chain:
- `.always()` advanced to the next card even when the API FAILED (progress lost,
  card skipped).
- `pointercancel` was bound to the same handler as `pointerup`, so a browser
  scroll-takeover on touch could commit an unintended answer.

### Fix (public/js/flashcard.js only)
- `resetCardPosition()` now resets `opacity` as well → new card starts at translateX(0)/opacity 1.
- `handleAnswer()`: advances ONLY in the API success callback; on failure it keeps the current card, restores position, clears `answered`/`submitting`, shows error → user can retry. Removed the `.always(nextCard)`.
- Added explicit `submitting` state; guards in `handleAnswer` + `handleSwipeStart` prevent double submission / multiple API calls.
- `flyOut()` is now purely visual and calls `handleAnswer(result)` immediately (removed the `setTimeout` hop); animation cleanup is handled by reset/render.
- Separate `pointercancel` listener that only resets drag state, never answers.
- No changes to scheduler, history, schema, or API contract.

### Tests
- Swipe right/left ≥100px → review recorded, next card visible ✔
- Swipe <threshold → no answer, card returns to center ✔
- Swipe before reveal → no answer ✔
- Rapid double swipe → single POST, single advance (`submitting` guard) ✔
- Correct/Wrong buttons and Arrow keys → same pipeline, unchanged behavior ✔
- API failure (server stopped) → error shown, card stays, retry works ✔
- Last card → queue reloads (existing end-of-session behavior) ✔

### Result
SUCCESS

## Vocabulary image flashcards

### Feature
Optional illustrative images on vocabulary cards (memory aid), sourced from
Wikimedia Commons with license/source/author metadata preserved. Admin
searches/selects in Management; Learn page only renders pre-selected URLs.

### Architecture
- `server/services/image/image.service.js` — provider abstraction +
  `normalizeImageMetadata` validation (url required, http/https only;
  javascript:/data:/file: rejected; null clears).
- `server/services/image/providers/wikimedia.provider.js` — default provider,
  no API key; uses MediaWiki API (`gsrnamespace=6`, imageinfo+extmetadata),
  node:https transport preferring IPv4.
- `server/routes/image.routes.js` → `GET /api/images/search?q=&limit=`,
  mounted in app.js.
- content.service: vocabulary validate accepts optional `image`.
- flashcard.js: image rendered between word and reading after reveal
  (`thumbnailUrl || url`), skeleton while loading, hidden on error, alt =
  "word - localized meaning", next card's image preloaded only.
- management.js: per-row "Search Image" button on vocabulary tab opens picker
  modal (query defaults to EN meaning → VI → romanization → word); thumbnail
  grid, select → preview + metadata + source link → Save / Remove via existing
  `PUT /api/vocabulary/:id {image}`.

### Data changes
- Backup first: data/backups/vocabulary.pre-image-2026-08-23.json.
- All 15 items got `"image": null`; 4 representative items filled with real
  Commons files: 本 (book), 辞書 (dictionary), 新聞 (newspaper stack),
  学校 (Japanese elementary school). IDs and all fields unchanged.

### API changes
- New endpoint only: GET /api/images/search. Content PUT/PATCH accepts
  optional validated `image` field — fully backward compatible.

### i18n
- New keys under `image.*` (vi/en): searchBtn, select, save, remove, selected,
  source, license, author, unavailable, noResults, loadError, searchPlaceholder.
  management.html now includes the i18n scripts.

### Tests
- GET /api/images/search?q=cat → normalized results with license/author ✔
- PUT image with `javascript:` URL → VALIDATION_ERROR ✔
- Save real image → persists in vocabulary.json; clear via image:null ✔
- random endpoint returns items incl. image metadata ✔
- node --check on all modified JS; backend modules load cleanly ✔
- Browser checks recommended: image display/fallback, swipe over image,
  tap-to-reveal, vi/en alt+meaning, Management search→select→save flow.

### Known issues
- Wikimedia thumbnails use fixed 480px width (fine for mobile).
- No local image caching yet (remote URLs only) — model allows adding later.
- Provider search quality depends on Commons search; admin picks manually.

## Study Sessions (lesson chunking)

### Feature / Reason
Large lessons exposed too many cards at once. Lessons are now split into
10-card study sessions for short daily practice. Content lessons are
unchanged (lesson field, IDs, records); sessions are a derived LEARNING view.

### Implementation
- `server/constants/study-session.js`: DEFAULT_SESSION_SIZE = 10 (central).
- `server/utils/session-chunker.js`: deterministic chunking; remainder kept
  as smaller final session. Verified: 5→[5], 10→[10], 11→[10,1],
  25→[10,10,5], 40→[10×4], 43→[10,10,10,10,3].
- `server/services/study-session.service.js`: derives sessions from
  id-sorted content on demand; per-session progress derived from existing
  card progress (`status !== 'new'`); no persistence, no duplicate records.
- `GET /api/learning/:uid/sessions?contentType&lesson` → list + progress;
  `.../sessions/cards?...&session=N` → only that session's items.
  Errors: LESSON_NOT_FOUND, SESSION_NOT_FOUND.
- Learn page: lesson select ("All lessons" = original random mode);
  lesson mode shows mobile session cards (✓/→/○ state, progress bar,
  Start/Continue, ≈N min estimate at 45 s/card, next session highlighted).
  Finishing a session returns to the refreshed overview; counter shows
  "L1 · S2 · 3 / 10". Review page independent of sessions (unchanged).
